<objective>
Activate the ADR 23 nested-scope mechanism that was pre-wired but stubbed in Phase 1. The Control Plane must: (1) intercept `task_spawned` events carrying `spawn_sub_scope: true` and create a child scope via the existing 3-phase nesting protocol with `parent_scope_id` set; (2) when a child scope's `scope_closed` lands, read `scope_lineage` for the parent and direct-write a `sub_scope_resolved` control-plane event to the parent partition; (3) route `sub_scope_resolved` rows to a dedicated topic so SubScopeResultWorker (Plan 06) can subscribe. This delivers the Control-Plane half of GATE4-3.

Purpose: Nested scopes let large sub-tasks run in isolated partitions and report results upward without parent Workers being aware of the child's physical existence (ADR 23). `sub_scope_resolved` is a control-plane signal injection — it does NOT add a sixth canonical event type (ADR 12 unchanged), exactly like `context_oom_throttled`.

Output: extended `nesting.ts` (sub-scope creation + sub_scope_resolved injection), extended `pulse-fetch.ts` (sub_scope_resolved topic routing), and `nesting.test.ts` covering child creation, parent linkage, and the resolved-signal write.
</objective>
