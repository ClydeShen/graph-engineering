## 第一优先级：阻塞型问题

### P0-D｜ADR 02 实现修正：`jsonb::text` 不保证字母序 key（新增，2026-05-31）
- **背景**：交叉验证发现 PostgreSQL 官方文档明确声明 `jsonb` 不保证任何特定 key 顺序，内部使用 length-first 排序（非字母升序）。ADR 02 哈希函数依赖 `canonical_json(payload)` 的字母序假设已被官方文档证伪。
- **决策**：✅ **已决策**（2026-05-31）——`canonical_json` 必须在应用层（Rust/TypeScript）通过 `BTreeMap` 递归序列化实现，PostgreSQL 侧接收已规范化 TEXT，**禁止在 PostgreSQL 内部做 `jsonb::text` 转换**。
- **影响范围**：ADR 02 已更新，Phase 1 Rust crate 和 TypeScript Worker 实现必须遵循。
- **状态**：✅ 已解决，ADR 02 已追加修正规范（含 Rust + TypeScript 代码）

### P0-A｜BM25 实现方案选型
- **背景**：两份 research 均确认 BM25 必须补入三张记忆表（episodic/semantic/procedural）的检索逻辑，与 pgvector 做双轨 RRF 融合。
- **决策**：✅ **已决策**（2026-05-31）——**方案 B：PostgreSQL 原生 `tsvector + ts_rank_cd`**，零额外依赖。在 RRF 0.6:0.4 权重、万到十万级短文本场景下，与真 BM25 的精度差距被 RRF 公式稀释，不可感知。后备升级路径：若实测发现技术术语召回率不足，无痛迁移至 `pg_search`（ParadeDB，可独立安装，无需完整 stack）。
- **影响范围**：ADR 20 BM25 补充规范已确认；三张记忆表加 `ts_doc tsvector GENERATED ALWAYS` 列。
- **状态**：✅ 已解决

### P0-B｜ADR 20 补充：BM25 + pgvector 双轨 RRF 混合检索规范
- **背景**：ADR 20 目前三张记忆表只有 pgvector HNSW 向量检索，缺少 BM25 轨道。
- **决策**：✅ **已决策**（2026-05-31）——**RRF k=60**（Cormack et al. 2009 学术标准值，Elasticsearch/OpenSearch/Weaviate 工业默认值）。结构：双路 RRF（vector_rank + bm25_rank）生成候选池，再叠加三信号重排（rrf_score × 0.6 + quality × 0.3 + recency × 0.1）。quality/recency 不放入 RRF，保留在重排层。
- **影响范围**：ADR 20 补充文档，RFC §4.4 双轨检索
- **状态**：✅ 已解决（完整 SQL 模板见 `.planning/research/verify-bm25-rrf.md`）

### P0-C｜发散性反思轨道的触发规范（问题21，已解决）
- **背景**：RFC §4.4 定义了三个触发场景（conflict_detected、macro-planning、冷启动），但触发后的完整流程未决策。
- **决策**：✅ **已决策**（2026-05-31）：
  1. **统一 `mem::reflect` 函数**（选项 A）：在 iii-engine 层实现，封装三表 RRF 查询 + Token 预算截断。Worker 只传入 `{query_text, query_embedding, trigger_type, w_max, scope_id}`，接收格式化注入内容。符合 RFC §2.1"大脑层"定位与 ADR 05 权限隔离。
  2. **注入规范**：预算 = `min(2000, W_max × 0.3)`，结构为 `[REFLECTION MEMORY]` 独立分区，Procedural > Episodic > Semantic 顺序截断。
  3. **Token 预算分配**：**顺序贪心截断**，不预设固定比例。Procedural 先取（LIMIT 1-3，天然上限），剩余预算给 Episodic（LIMIT 5），再剩给 Semantic（LIMIT 5）。总计通常在 600-1200 tokens，远低于 2000 token 上限。触发类型差异化：`conflict_detected` 上限降为 `min(1000, W_max × 0.2)`。
- **影响范围**：ADR 21 已归档（`docs/adr/0022-adr21-reflection-track-trigger-spec.md`）
- **状态**：✅ 已解决，ADR 21 已写入

### P1-A｜iii-engine 可用 Worker 验证
- **背景**：`harness` 模块中的四个潜在组件：`llm-budget`、`context-compaction`（对应 ADR 14/16）、`approval-gate`（审批门）、`turn-orchestrator`（多回合协调器）
- **决策**：✅ **已解决**（2026-05-31 Round 2 验证）——**以上四个组件均不在公开 iii 注册表中**。公开注册表仅含基础设施 Worker（postgres、redis、kafka 等 19 个）。`approval-gate` 是 iii 的**设计模式**（在 condition function 中显式检查），不是可下载的 Worker 二进制。`llm-budget`/`context-compaction`/`turn-orchestrator` 必须作为**自建 iii Functions** 实现。

- **影响范围**：ADR 14/16 备注更新："实现为自建 iii Function，非注册表 Worker"。Phase 1 工作量含 llm-budget Function 构建。
- **状态**：✅ 已解决（无法从注册表简化，均需自建）

### P1-B｜Pi 沙箱预演模式与 OCC 的关系
- **背景**：利用 Pi 沙箱在不污染 PostgreSQL 主账本的前提下模拟推进图拓扑，确认无冲突后批量提交
- **分析**（2026-05-31 Round 2）：
  1. **实现路径已明确**：Pi SDK 的 `runtime.fork(entryId)` + `SessionManager.inMemory()` 可在内存中预演图拓扑，不写入 PostgreSQL。
  2. **与 ADR 03 关系**：预演在 PostgreSQL 外部（纯内存），批量提交仍走 Writable CTE OCC。预演是 OCC 冲突的"预检"，减少无效提交尝试，不替代 OCC 原子性保证。
  3. **原子性保证**：提交时仍需完整 OCC CAS 验证（其他 Worker 可能并发写入，预演结果不保证最新状态）。
- **结论**：值得引入，但属于 Phase 4 优化项，不阻塞 Phase 1-3。Phase 4 规划时补写 ADR（Pi Sandbox ADR）。
- **影响范围**：新增 ADR（Phase 4），ADR 03 无需修改
- **状态**：🟢 降级为 Phase 4 追踪项，不阻塞 Phase 1

### P1-C｜iii-database worker 的 change feeds 与 ADR 09 的关系
- **背景**：Pi research 提到 iii-database worker 支持 change feeds，可能替代 LISTEN/NOTIFY
- **决策**：✅ **已解决**（2026-05-31 Round 2 验证）——**ADR 09 LISTEN/NOTIFY + HWM 设计正确，无需修订**。iii 的 `postgres` worker 触发器类型为 `sql::query::execute`（查询级事件），不是行级 CDC。iii 内部的"change feeds"指的是 `iii-stream` 的 `StreamChangeEvent`（iii 自身 KV 数据变更），与 PostgreSQL 无关。PostgreSQL 原生支持 WAL 逻辑复制 CDC，但开销远高于 LISTEN/NOTIFY，且对 append-only event log 属于过度设计。
- **影响范围**：ADR 09 无需修改。tokio-postgres 集成已确认（`poll_message()`）。
- **状态**：✅ 已解决（ADR 09 设计正确）

### P1-F｜SHA-256 dedup 去重窗口补入实施规范
- **背景**：agentmemory 在捕获原始观察时，先执行 SHA-256 去重（5分钟窗口），防止相同工具调用被重复存入 Working Memory
- **分析**（2026-05-31 Round 2）：
  - **已有结构去重**：版本哈希公式 `SHA256(scope|entity|predecessor|event_type|canonical_json(payload))` 包含 predecessor_hash，同一祖先下相同写入自然被 unique constraint 拦截。
  - **未覆盖场景**：相同工具调用发生在不同祖先节点（不同前驱），会产生不同 version_hash → 版本哈希去重失效。对 Working Memory 高频工具调用可能产生语义重复记录。
  - **agentmemory 解法**：去重 hash = `SHA256(scope_id|entity_id|event_type|payload_hash)` + 5 分钟 `created_at` 窗口过滤（不含 predecessor_hash）。
  - **Phase 1 决策**：不实现时间窗口去重，依赖结构去重。Phase 2 补入 Working Memory 时间窗口去重（5 分钟窗口，ADR 11 补充）。
- **影响范围**：ADR 11 补充规范（Phase 2）
- **状态**：🟡 Phase 1 暂不实现，Phase 2 补入 ADR 11

## 第三优先级：可选增强项

### G1｜无遍历代数（Traversal Algebra）— Cayley 对照缺口
- **背景**：Knapsack Slicing 是固化的 SQL 算法，无法表达临时图遍历查询（如"找出过去 30 个 Scope 内所有连续 3 次冲突的实体链"、"跨域拓扑中 explore→hypothesize→validate→converge 的实例计数"）。Cayley（Gizmo API）展示了一个完备的遍历代数（morphism、filter、multi-hop 路径表达式）。
- **阻塞范围**：Phase 2 CrossScopePatternDiscoveryWorker 要做跨 Scope 的拓扑对比，当前只有 HNSW 向量相似度——向量查询无法表达精确的结构性图查询。
- **Phase 1 影响**：无直接阻塞。Phase 1 schema（execution_event_log + 索引）设计不应封闭未来添加图查询层的可能性。
- **状态**：🟡 Phase 2 前置研究，不阻塞 Phase 1

### G2｜无形式化模式定义语言（Pattern Definition Language）— Peregrine 对照缺口
- **背景**：TemplateProposalWorker 使用 LLM 定性提取执行模式，输出的 `template_graph` 是非结构化 JSON。Peregrine（FSM）展示精确的子图模式挖掘：声明式描述模式（edge-list 格式），运行时精确枚举所有匹配。
- **问题**：两次 TemplateProposalWorker 对结构上相同的 DAG 可能提取出语义相近但字面不同的模板，导致 `topology_embedding` 相似度高但 `template_graph` 无法机器比对。模式涌现的可验证性为零。
- **Phase 1 影响**：无直接阻塞。`template_graph` 的 JSONB 字段格式留余地（避免固化为不可解析的 LLM 散文）。
- **状态**：🟡 Phase 2 前置研究（与 G1 遍历代数协同设计），不阻塞 Phase 1

### G4｜无物化遍历路径（Materialized Traversal Cache）— codegraph 对照缺口

- **缓解路径**：Phase 2 可考虑 predecessor chain 的物化视图（`CREATE MATERIALIZED VIEW scope_lineage_view`）或 Redis 内存缓存（最近 N 个 predecessor）。
- **状态**：🟢 Phase 2 性能优化，Phase 1 无阻塞

### P2-E｜iii-cron worker 集成：Ebbinghaus 衰减扫描的调度规范
- **背景**：Semantic/Procedural Memory 需要定期扫描低 reinforcement_count 或长期未使用的记忆，执行衰减
- **方案明确**（2026-05-31 Round 2）：
  - **调度**：每日凌晨 3 点（错开归纳扫描）：`expression: '0 0 3 * * * *'`
  - **衰减阈值**：`reinforcement_count = 0` AND `last_used_at < NOW() - INTERVAL '90 days'`
